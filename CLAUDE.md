# WebOpt Lab

A React app that teaches web performance tricks with live demos. Each demo has a slow and a fast version
of the same feature: the user interacts on the left and watches live metrics (frame rate, main-thread
load, memory, DOM size) on the right.

Everything runs in the browser. **There is no server.** Data is generated client-side by a fake API.

## Commands

```sh
npm run dev       # dev server on http://localhost:5173
npm run build     # type-check (tsc --noEmit) + production build
npm run preview   # serve the production build on :4173 (use this for realistic numbers)
```

Stack: Vite 8, React 19, TypeScript 7, Tailwind CSS v4 (`@tailwindcss/vite`, configured in
`src/index.css`, no config file), `@tanstack/react-query`, `@tanstack/react-virtual`. Dark theme only.

### Test results page (`/results.html`)

The page shows a plain-language view of the latest test run: a summary, the three versions, what is tested,
the correctness table, speed tables with bars, the remaining checks (collapsed `<details>`), and a glossary.
**It is intentionally React-free** so it stays lightweight. It has one small script, the shared CSS, and its
data is bundled, so there is no fetch. Plain-language names for the feature tests live in `FEATURE_TEXT` in
`src/results/main.ts`. When you add or rename a feature test, add its entry there.
The demo links to it with a dashed emerald "📊 Test results" link next to the tabs, styled so it doesn't
look like a fourth tab.

## Trick #1: Rendering huge lists

The same data is shown three ways, and only one is mounted at a time:

| Tab | How it loads data | What it renders |
|---|---|---|
| Without TanStack Query | `fetchAllUsers(total)`: one response, 400 ms delay | every row |
| TanStack Query | `useInfiniteQuery`, 200 rows per page, 150 ms delay | every loaded row |
| TanStack Query + Virtual | same as above | visible rows + `overscan: 8` |

The key lesson: **TanStack Query fixes fetching and caching, not rendering.** Virtualization fixes rendering.
The middle tab exists to show this. It starts fast, then gets slower as you scroll.

### Mock data

`makeUser(i)` seeds a PRNG (mulberry32) with the row index, so row N is always identical. Each row has about
12 fields, including nested `address` and a `tags` array, so it has a realistic memory footprint.

### Metrics and what they mean

Browsers don't expose real CPU usage to JavaScript, so these are proxies:

- **Frame rate:** frames counted with `requestAnimationFrame`.
- **Main thread busy %:** time spent in Long Tasks (`PerformanceObserver` type `longtask`, Chromium only)
  divided by the sample window. This is the "CPU" number.
- **JS heap:** `performance.memory.usedJSHeapSize`, Chrome/Edge only.
- **DOM nodes in list:** `getElementsByTagName('*').length` on the list area.
- **React commits / commit time:** `<Profiler>` around the list.
- **Click → paint:** `measureInteraction()` in `probe.ts`: time from click until rAF, then a setTimeout after paint.
- **Longest task / Total blocking time:** taken from the Long Tasks entries.

## Decisions (and why)

- **No `<StrictMode>`.** Its double-run effects and renders would inflate the numbers being measured.
- **`react-dom/client` is aliased to `react-dom/profiling`** in `vite.config.ts`, so `<Profiler>` timings
  still work in production builds.
- **A fresh `QueryClient` and `Probe` per run** (`runKey = mode-total-run`), so every run starts cold.
- **`UserRow` is not memoized.** The demo shows what an ordinary row costs. Memoization is a future trick.
- **The sparklines are hand-written SVG.** A chart library would add its own load to the measurements.
- **The naive tab waits for a "Mount N rows" click.** It never mounts on page load.
- **The default row count is 10k.** The options are 10k / 25k / 50k / 100k.

## Bugs found and fixed (do not reintroduce)

1. **Page crash: metrics state re-rendered the list.** `useMetrics` used to live in `LargeListDemo`,
   which also renders the list. Every 500 ms sample re-rendered all rows. With 50k rows, each re-render took
   longer than 500 ms, the work piled up, and the tab died.
   **Rule:** sampled metrics state must live in its own component (`LiveMetrics`). The list sits behind a
   `memo`'d `ListHost`, so parent state changes (auto-scroll toggle, etc.) don't re-render it.
2. **Constant repaint after mount.** With 500k nodes mounted, the page stayed at about 20 fps and 41% busy
   while idle. A Chrome trace showed Paint, PrePaint and compositing running every frame: small changes
   elsewhere on the page (the pulsing FPS dot, the gradient title, the metric updates) made Chrome re-walk
   the whole list. **Fix:** `[contain:strict]` on the fixed-height list area. Idle went back to about 57 fps
   and 0% busy.

## Measured numbers (headless Chrome, desktop, production build)

Naive tab, time to mount:

| Rows | Freeze | Heap | DOM nodes |
|---|---|---|---|
| 10k | ~2.4 s | ~62 MB | 100k |
| 50k | ~17 s | ~293 MB | 500k |
| 100k | ~78 s (triggers Chrome's "Page unresponsive" dialog) | ~549 MB | 1M |

For 50k rows, about 10 s of the freeze is React creating DOM nodes, about 5 s is style and layout, and about
5 s is paint and compositing. React's own render phase (Profiler) is only about 1.8 s.

Clicking a row, 10k rows, dev server:

| Tab | Click → paint |
|---|---|
| Without TanStack Query | ~806 ms |
| TanStack Query + Virtual | ~41 ms |

## Why a row click is slow in tabs 1 and 2 but not 3

`selectedId` is state in the list component. `setSelectedId` re-renders the list, and `users.map(...)`
builds a new `<UserRow>` for **every rendered row**. `UserRow` isn't memoized, so React re-runs and diffs
every row only to find that 2 rows changed (the old selection and the new one). The cost scales with the
number of **rendered** rows:

- Tab 1 renders all 10k rows.
- Tab 2 renders every loaded row, and the count grows as you scroll.
- Tab 3 renders about 25 rows.

There's also a fix without virtualization: `memo(UserRow)` plus `useCallback` for `onSelect`. Both are
needed. A new `onSelect` function on every render would break `memo`. With both, only 2 rows re-render.

## Known limitations

- Heap readings carry over between tabs, because freed memory isn't garbage-collected right away. Reload
  the page between tabs for a clean memory comparison. (An in-app note about this has not been added yet.)
- Heap and long-task metrics only work in Chromium. The panel shows a notice in other browsers.
- Dev mode numbers are inflated. Use `npm run build && npm run preview` for realistic ones.
- There is no favicon yet, so the console logs a harmless 404.

## Tests (Playwright)

```sh
npm run test:e2e      # everything, ~15 min
npm run test:quick    # everything except @perf, ~10 min
npm run test:report   # rebuild TEST-MATRIX.md from test-results/results.json
```

- The config (`playwright.config.ts`) builds the app and serves it with `vite preview` on :4173. It uses
  the installed Chrome (`channel: 'chrome'`), the en-US locale and **one worker**, so tests don't compete
  for CPU.
- `tests/home.spec.ts` covers the header, hero, trick cards and mobile layout. `tests/demo-controls.spec.ts`
  covers the tabs, mount gate, restart, auto-scroll and metrics panel.
- `tests/list-modes.spec.ts` is the feature × tab matrix. Test titles must end in `[naive|query|virtual]`.
- `tests/perf.spec.ts` (`@perf`) is the tab × row-count matrix. It uses `--expose-gc` so heap readings
  show retained memory.
- Test hooks in the app: `data-testid` = `user-row` / `list-scroll` / `list-area`, plus `data-id` and
  `data-selected` on rows, and `data-metric` + `data-value` on each metric in the panel.
- Don't pass `--reporter=...` on the CLI: it replaces the JSON reporter, and then the report has no input.
- The perf matrix measures naive only up to 25k (`NAIVE_MAX` in `perf.spec.ts`). Naive 50k and 100k did
  not finish within 5 / 15 min on the dev laptop (i3-1215U, 8 GB RAM), so the user chose to remove those
  cells. This is the naive approach running out of memory, not a bug.
- Bugs the suite found and that are now fixed: the naive gate was skipped when returning to the naive tab;
  auto-scroll stopped early in paged tabs when it caught up with the loaded rows (it now requires the
  bottom to hold for 1 s).
